# Database Implementation Plan

## Goal

Replace the backend's process-local item store with a Dockerized local database. Keep the existing HTTP API contract unchanged so the frontend continues to work without code changes.

## Current State

The backend is a single FastAPI module in `backend/main.py`.

- `GET /items` reads from an in-memory `dict[int, Item]`.
- `POST /items`, `PUT /items/{item_id}`, and `DELETE /items/{item_id}` mutate that dictionary.
- Item IDs come from a process-local integer counter.
- All item data is lost whenever the backend restarts.
- The frontend calls only `/items` through the Vite `/api` proxy. Its expected item shape is `{ id: number, name: string, description: string | null }`.
- There are no database, migration, seed, or backend test files yet.

## Recommendation: PostgreSQL

Use PostgreSQL rather than MongoDB.

PostgreSQL is the better fit because items have a stable, relational schema; item IDs and uniqueness constraints belong naturally in SQL; and Alembic provides an explicit migration history. This also makes useful learning exercises such as constraints, transactions, indexes, and migrations visible.

MongoDB would provide less value for item CRUD and would weaken the migration/constraint portion of this exercise.

## Target Architecture

Use these components:

- PostgreSQL 16 in Docker Compose with a named volume and health check.
- SQLAlchemy 2.x async ORM for application queries.
- `asyncpg` as the PostgreSQL driver.
- Alembic using its async template for versioned schema migrations.
- `pydantic-settings` for `DATABASE_URL` and environment configuration.
- A separate, idempotent Python seed command.
- FastAPI lifespan setup for engine disposal. Schema creation must remain Alembic's responsibility; do not call `create_all()` at application startup.

## Database Schema

### `items`

| Column        | Type                                      | Constraints |
| ------------- | ----------------------------------------- | ----------- |
| `id`          | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | primary key |
| `name`        | `TEXT`                                    | not null    |
| `description` | `TEXT`                                    | nullable    |

Return only `id`, `name`, and `description` from the API. Database-generated identity values replace the global `next_id` counter.

## API Compatibility Requirements

Do not change frontend files or route paths.

- `GET /items` returns `200` and a JSON array ordered by ascending `id`.
- `POST /items` accepts the existing `ItemIn` body and returns the existing `Item` body with `201`.
- `GET /items/{item_id}` returns the existing item shape or `404 {"detail":"Item not found"}`.
- `PUT /items/{item_id}` remains a full replacement of `name` and `description`, returning the existing item shape or the same 404 response.
- `DELETE /items/{item_id}` returns `204` with no body, or the same 404 response.
- Continue serving the Vite proxy arrangement and current CORS origins unchanged.

Define an explicit Pydantic response model for items.

## Migration Plan

Run the commands in this plan from `backend/` unless a step says otherwise.

1. Add dependencies with:

   ```bash
   uv add sqlalchemy asyncpg alembic pydantic-settings
   uv add --dev pytest pytest-asyncio
   ```

2. Add `backend/compose.yaml` with a `db` service based on `postgres:16-alpine`:
   - Read database name, user, password, and published port from environment variables with development defaults.
   - Publish port `5432` for local backend access.
   - Persist `/var/lib/postgresql/data` in a named volume.
   - Add a `pg_isready` health check.
   - Do not commit real credentials.

3. Add `backend/.env.example` containing non-secret local defaults and an async URL such as:

   ```dotenv
   POSTGRES_DB=fastapi_uv
   POSTGRES_USER=fastapi_uv
   POSTGRES_PASSWORD=fastapi_uv_dev
   POSTGRES_PORT=5432
   DATABASE_URL=postgresql+asyncpg://fastapi_uv:fastapi_uv_dev@localhost:5432/fastapi_uv
   ```

4. Initialize Alembic with the async template:

   ```bash
   uv run alembic init -t async alembic
   ```

   Configure `alembic/env.py` to load the URL from application settings and set `target_metadata` to the SQLAlchemy declarative base metadata.

5. Create a hand-reviewed initial migration for the items table, checks, and indexes. Include complete `upgrade()` and `downgrade()` operations.

6. Verify migration lifecycle against an empty container:

   ```bash
   docker compose up -d db
   until [ "$(docker inspect --format='{{.State.Health.Status}}' "$(docker compose ps -q db)")" = "healthy" ]; do sleep 1; done
   docker compose ps
   uv run alembic upgrade head
   uv run alembic current
   uv run alembic downgrade base
   uv run alembic upgrade head
   ```

There is no durable item data to migrate from the current dictionary. If the server is presently holding manually entered items, export them before stopping that process and convert them into `seeds/items.json`; otherwise they cannot be recovered after restart.

## Data Seeding Plan

Check seed data into source control so setup is deterministic and does not require internet access.

- `seeds/items.json` contains a few representative records, including one with a null description. It may be an empty array if a blank frontend is preferred.
- `python -m app.seed` validates the file with Pydantic before writing anything.
- Run the seed in one transaction.
- Upsert item rows by explicit `id`, then branch on table contents when resetting the identity sequence: use `MAX(id) + 1` as its next value when rows exist, or reset it to its initial value when `seeds/items.json` is empty and no rows are present.
- Running the seed command repeatedly must produce the same rows without duplicates.
- A malformed file must fail the command and roll back the entire seed transaction.

Do not run seeding automatically on every API startup. Keep migration, seeding, and serving as separate observable learning steps:

```bash
docker compose up -d db
until [ "$(docker inspect --format='{{.State.Health.Status}}' "$(docker compose ps -q db)")" = "healthy" ]; do sleep 1; done
uv run alembic upgrade head
uv run python -m app.seed
uv run fastapi dev main.py
```

## Backend Refactor Steps

1. Move request/response models out of `main.py` into `app/schemas.py`. Preserve all existing field names, nullability, status codes, and error details.
2. Define SQLAlchemy models and constraints in `app/models.py`.
3. Create settings, async engine, session factory, and a `get_session()` FastAPI dependency in `app/config.py` and `app/database.py`.
4. Implement repository functions for item CRUD. Commit write transactions explicitly and refresh newly created rows before serialization.
5. Replace dictionary access and `next_id` in each item route with injected `AsyncSession` operations.
6. Remove `httpx` as a direct dependency now that no route makes an external request; it may remain available transitively for FastAPI tests, but test dependencies should be declared intentionally.
7. Keep the root route intentionally removed and leave unrelated learning modules unchanged.

## Test Plan

Use a dedicated PostgreSQL test database, not SQLite. SQLite would hide PostgreSQL-specific behavior such as identity handling, numeric precision, constraints, and SQL syntax.

### Migration checks

- Upgrade a blank test database to `head`.
- Confirm all tables, constraints, and indexes exist.
- Downgrade to `base`, then upgrade to `head` again.

### Seed checks

- Seed an empty database and verify the expected item count.
- Run the seed twice and verify counts do not change.
- Verify the next created item ID does not collide with seeded IDs.
- Verify invalid seed data rolls back without partial writes.

### API checks

- List items from seeded data in ascending ID order.
- Create, retrieve, update, and delete an item through the API.
- Assert nullable descriptions and 404 bodies remain unchanged.
- Assert delete returns an empty `204` response.
- Monkeypatching `httpx` should be unnecessary because no route makes an external data request.

### Frontend regression check

With the migrated and seeded database running:

```bash
cd frontend
npm run build
npm run dev
```

Open the app through Vite and manually verify list, create, edit, and delete. No frontend source changes should appear in the feature diff.

## Documentation and Developer Workflow

Update `backend/README.md` with prerequisites, environment setup, first-run commands, reset commands, and troubleshooting. Keep the root README as a concise repository overview linking to the backend and frontend instructions. Include these common workflows:

```bash
# Start only the database
docker compose up -d db
until [ "$(docker inspect --format='{{.State.Health.Status}}' "$(docker compose ps -q db)")" = "healthy" ]; do sleep 1; done

# Apply schema and seed local data
uv run alembic upgrade head
uv run python -m app.seed

# Inspect service health and logs
docker compose ps
docker compose logs db

# Reset all local database data, then rebuild it
docker compose down -v
docker compose up -d db
until [ "$(docker inspect --format='{{.State.Health.Status}}' "$(docker compose ps -q db)")" = "healthy" ]; do sleep 1; done
uv run alembic upgrade head
uv run python -m app.seed

# Stop without deleting data
docker compose down
```

Add `.env` to `.gitignore`, while committing `backend/.env.example`. Document that the backend runs on the host and reaches PostgreSQL through `localhost`; if the backend is containerized later, its database host must change to the Compose service name `db`.

## Definition of Done

- PostgreSQL starts from one Docker Compose command and reports healthy.
- Alembic can upgrade a blank database, downgrade it, and upgrade it again.
- Seeding succeeds offline, is transactional, and is idempotent.
- Item data survives backend and database container restarts.
- All existing route paths, item payloads, status codes, and errors remain compatible.
- Backend tests pass against PostgreSQL.
- The frontend builds and completes its existing CRUD workflow without source changes.
- Setup, reset, migration, seed, and run commands are documented.

## Suggested Implementation Order

1. Add Compose and environment configuration.
2. Add SQLAlchemy models and database session setup.
3. Add and validate the initial Alembic migration.
4. Add static seed fixtures and the idempotent seed command.
5. Move item CRUD to PostgreSQL while preserving response models.
6. Add migration, seed, and API tests.
7. Run the backend and frontend regression checks, then finish the root README.
